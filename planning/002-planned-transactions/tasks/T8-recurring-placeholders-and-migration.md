## Description

Stop `generate_pending` from recording future occurrences as settled, and reclassify the rows it has
already written.

## Implementation guidance

**The defect.** `recurring_transaction_service.generate_pending` (lines 189-264) materializes
occurrences as real `Transaction` rows with `source="recurring"`, and `up_to` explicitly allows
generating into the future — *"This allows the dashboard to pre-generate transactions for future
months when the user navigates ahead"* (lines 193-194). Those rows never set `status`, so they
inherit the column default `posted`. A transaction that has not happened is stored as settled.

**Fix.** Set `status="planned"` for occurrences dated after today, `posted` otherwise. Occurrences
that fall on or before today are genuinely due and keep current behavior.

**Migration** — new file in `backend/alembic/versions/`, following the conventions of the 66 existing
migrations:

```sql
UPDATE transactions
   SET status = 'planned'
 WHERE source = 'recurring'
   AND date > CURRENT_DATE
   AND status = 'posted';
```

Downgrade reverses on the same predicate. Log the affected row count.

**Scope it to `source = 'recurring'`.** Manually entered future-dated rows are deliberately left
alone: the user never had a way to express intent about them, so reclassifying them would be a guess
about data the user entered under different semantics.

Note the `status = 'posted'` guard in the predicate — it keeps the migration idempotent and avoids
touching any row a user has already adjusted.

Check whether the Celery beat task (`app/tasks/recurring_tasks.py`, scheduled every 60s per
`app/worker.py:28`), the CLI entry point (`app/cli.py:13`) and `POST /recurring_transactions`
(`app/api/recurring_transactions.py:80`) all route through `generate_pending`. If any writes rows by
another path, it needs the same treatment.

## Done when

Satisfies: *"Placeholders generated by generate_pending for dates after today are created in the
planned state, not posted"*, *"A migration reclassifies existing future-dated recurring placeholders
to planned, leaving past-dated rows and all non-recurring rows untouched"*, and *"The migration is
reversible and reports how many rows it changed."*

Verified by: `generate_pending` with a future `up_to` produces planned rows for future dates and
posted rows for past ones. Migration test seeded with four rows — future recurring, past recurring,
future manual, past manual — asserts only the first changes, and that downgrade restores the original
state.

## Notes

This is a product correctness fix. It does not serve the manual-entry workflow that motivates the
spec (see D4), so its value is independent of the rest of the feature — but it shares the status
semantics, which is why it belongs here rather than in its own spec.
